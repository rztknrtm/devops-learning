# GIT — краткий конспект DevOps

## 1. Что такое Git

**Git** — распределённая система контроля версий (DVCS).

Назначение:
- Хранение истории изменений проекта.
- Совместная разработка.
- Создание и объединение веток.
- Возврат к предыдущим состояниям.
- Контроль изменений конфигураций, кода, YAML-файлов и документации.

**Git ≠ GitHub.**

- Git — система контроля версий.
- GitHub / GitLab / Bitbucket — платформы для хранения удалённых репозиториев, совместной разработки и CI/CD.

## 2. Как Git работает под капотом

Git хранит данные в скрытой директории `.git`.

Основные составляющие:

| Компонент | Назначение |
|---|---|
| Working Directory | Рабочие файлы проекта |
| Staging Area (Index) | Подготовленные изменения для следующего коммита |
| Local Repository | История коммитов и объекты Git |
| Remote Repository | Удалённая копия репозитория |

### Внутреннее устройство Git

Git использует объектную модель:

- **Blob** — содержимое файла.
- **Tree** — структура директорий и ссылки на файлы и поддиректории.
- **Commit** — снимок состояния проекта, ссылка на Tree, родительские коммиты, автор, дата и сообщение.
- **Tag** — метка определённого коммита (Annotated Tag является отдельным объектом Git).

Объекты идентифицируются хешами. Git может повторно использовать уже существующие объекты с одинаковым содержимым.

**Важные указатели:**

- `HEAD` — показывает текущее положение в истории, обычно указывает на текущую ветку.
- `master` / `main` — указатель на последний коммит соответствующей ветки.
- `origin/master` — локальная ссылка на последнее известное состояние удалённой ветки master.

### Как сохраняются изменения

```text
Working Directory
       |
    git add
       ↓
  Staging Area
       |
   git commit
       ↓
 Local Repository
       |
    git push
       ↓
 Remote Repository
```

`git add` помещает текущее содержимое файла в Index. Последующие изменения файла автоматически туда не попадают.

`git commit` создаёт объект коммита на основе подготовленного состояния.

**Важно:** коммит хранит снимок состояния проекта, а не просто список текстовых изменений.

## 3. Основные команды Git

### Создание и настройка

| Команда | Назначение |
|---|---|
| `git init` | Создать локальный репозиторий |
| `git clone URL` | Клонировать существующий репозиторий |
| `git config --global user.name "Name"` | Настроить имя автора |
| `git config --global user.email "email"` | Настроить email автора |
| `git config --list` | Посмотреть настройки |

`user.name` и `user.email` — информация об авторе коммитов, не учётные данные GitHub.

### Основной рабочий цикл

| Команда | Назначение |
|---|---|
| `git status` | Проверить состояние репозитория |
| `git add file` | Добавить файл в Staging Area |
| `git add .` | Подготовить изменения текущей директории |
| `git commit -m "message"` | Создать коммит |
| `git log --oneline --graph --decorate` | Посмотреть историю |
| `git diff` | Показать незастейдженные изменения |
| `git diff --staged` | Показать подготовленные изменения |
| `git show HASH` | Посмотреть конкретный коммит |

### Удалённые репозитории

| Команда | Назначение |
|---|---|
| `git remote -v` | Показать удалённые подключения |
| `git remote add origin URL` | Добавить удалённый репозиторий |
| `git remote rename old new` | Переименовать подключение |
| `git fetch origin` | Получить изменения и обновить ссылки удалённых веток |
| `git pull` | Получить изменения и интегрировать их в текущую ветку |
| `git push` | Отправить локальные коммиты |
| `git push -u origin branch` | Отправить ветку и настроить upstream |

**Origin** — общепринятое имя удалённого подключения, а не отдельный сервер.

`fetch` не обновляет рабочие файлы и текущую ветку.

`pull` = fetch + интеграция (обычно merge, возможен rebase).

`push` отправляет коммиты и обновляет соответствующие ссылки удалённого репозитория.

### Ветки (Branches)

Ветка Git — указатель на коммит, а не отдельная физическая копия проекта.

| Команда | Назначение |
|---|---|
| `git branch` | Посмотреть локальные ветки |
| `git branch -a` | Посмотреть локальные и удалённые ветки |
| `git branch name` | Создать ветку |
| `git switch name` | Переключиться на ветку |
| `git switch -c name` | Создать ветку и переключиться |
| `git branch -d name` | Удалить локальную ветку |

### Merge

Объединение изменений двух веток.

**Fast-forward:**
- Текущая ветка является предком объединяемой.
- Git просто передвигает указатель вперёд.
- Отдельный merge commit не создаётся.

**Three-way merge:**
- Истории веток разошлись.
- Git использует общего предка и два набора изменений.
- При успешном слиянии создаётся merge commit с двумя родителями.

**Merge Conflict:**
- Git не может автоматически согласовать изменения.
- Требуется ручное разрешение.

После исправления:

```bash
git add conflicted-file
git merge --continue
```

Альтернатива — после добавления исправленных файлов выполнить `git commit`.

Отмена незавершённого слияния:

```bash
git merge --abort
```

### Rebase

Перенос коммитов текущей ветки поверх другой базы.

```bash
git fetch origin
git switch feature
git rebase origin/main
```

Особенности:
- Создаёт новые версии переносимых коммитов.
- Хеши перенесённых коммитов меняются.
- Позволяет получить линейную историю.
- Не следует без согласования переписывать историю общих опубликованных веток.

Если возник конфликт:

```bash
git status
# Исправить файл
git add file
git rebase --continue
```

Отмена:

```bash
git rebase --abort
```

**Merge сохраняет разветвлённую историю. Rebase переписывает историю переносимых коммитов.**

### Cherry-pick

Перенос изменений конкретного коммита в текущую ветку.

```bash
git switch main
git cherry-pick COMMIT_HASH
```

Особенности:
- Переносится изменение выбранного коммита относительно его родителя.
- Предыдущие и последующие коммиты автоматически не переносятся.
- Создаётся новый коммит с новым хешем.
- Возможны конфликты.

### Revert

Безопасная отмена опубликованного коммита.

```bash
git revert COMMIT_HASH
```

Создаёт новый коммит с обратными изменениями. Исходный коммит остаётся в истории.

### Reset

Перемещение указателя текущей ветки к другому коммиту.

| Команда | Результат |
|---|---|
| `git reset --soft HEAD~1` | Убирает последний коммит, сохраняет изменения в Staging Area |
| `git reset --mixed HEAD~1` | Убирает коммит, сохраняет изменения в Working Directory |
| `git reset --hard HEAD~1` | Убирает коммит и сбрасывает Index и Working Directory |

`--mixed` используется по умолчанию.

`HEAD~1` — родитель текущего коммита.

**Reset не обязательно физически удаляет объекты коммитов сразу. Восстановить прежние положения указателей можно через `git reflog`.**

Не использовать `reset --hard` без понимания последствий.

### Дополнительные команды

| Команда | Назначение |
|---|---|
| `git checkout branch` | Старый способ переключения веток |
| `git restore file` | Восстановить файл |
| `git fetch --all` | Получить обновления со всех настроенных remote |
| `git clone URL` | Скачать репозиторий |
| `git reflog` | Посмотреть историю перемещения HEAD |
| `git cherry-pick HASH` | Применить выбранный коммит |

## 4. Tags

Теги используются для маркировки конкретных версий проекта.

Примеры: `v1.0.0`, `v1.1.0`, `v2.0.0`.

**Lightweight Tag:**

```bash
git tag v1.0.0
```

Простой указатель на коммит.

**Annotated Tag:**

```bash
git tag -a v1.0.0 -m "Release 1.0.0"
```

Содержит отдельную метаинформацию: автора, дату, сообщение. Удобен для релизов.

Другие команды:

```bash
git tag
git show v1.0.0
git push origin v1.0.0
git push origin --tags
git tag -f v1.0.0 COMMIT_HASH
```

Тег не перемещается автоматически при появлении новых коммитов.

Если опубликованный тег перемещён локально, для обновления удалённого потребуется force push. Это требует согласования команды.

## 6. Стратегии ветвления

**GitHub Flow**
- Основная ветка main.
- Короткоживущие feature-ветки.
- Pull Request.
- Code Review и CI.
- Merge после проверки.

**GitLab Flow**
- Основная ветка и процесс Merge Request.
- Может учитывать окружения и релизные ветки.
- Конкретная модель зависит от проекта.

**GitFlow**
- `main` — релизы.
- `develop` — интеграция разработки.
- `feature` — новые функции.
- `release` — подготовка релиза.
- `hotfix` — срочные исправления.

**Trunk-Based Development**
- Частая интеграция небольших изменений в общую основную ветку.
- Короткоживущие ветки или работа непосредственно с trunk.
- Автоматические тесты.
- Feature Flags для управления доступностью незавершённого функционала.

## 7. Pull Request / Merge Request

Pull Request (GitHub) / Merge Request (GitLab) — запрос на рассмотрение и объединение изменений одной ветки в другую.

Типовой процесс:

```text
Create feature branch
       ↓
Make changes
       ↓
Commit
       ↓
Push
       ↓
Pull Request
       ↓
Code Review + CI Tests
       ↓
Merge
```

`git push` — отправка коммитов.

Pull Request — процесс проверки и запроса на интеграцию. Это не отдельная ветка и не коммит.

## 8. Типовые вопросы собеседования

**Как работает git pull?**

Выполняет получение изменений через fetch и интеграцию их в текущую ветку через merge или rebase.

**Чем отличаются merge и rebase?**

Merge объединяет истории и сохраняет их разветвление. Rebase повторно применяет коммиты поверх новой базы, переписывая их хеши.

**Что такое merge conflict?**

Ситуация, в которой Git не может автоматически объединить изменения. Требуется ручное разрешение.

**Как перенести один коммит между ветками?**

`git cherry-pick COMMIT_HASH`.

**Как отменить опубликованный коммит?**

`git revert COMMIT_HASH`.

**Чем reset отличается от revert?**

Reset перемещает указатель ветки. Revert создаёт новый коммит, отменяющий изменения.

**Что такое staging area?**

Промежуточная область подготовки изменений к коммиту.

**Чем clone отличается от init?**

Init создаёт новый локальный репозиторий. Clone скачивает существующий репозиторий с историей и автоматически настраивает origin.

**Что такое origin?**

Имя удалённого подключения, обычно указывающее на исходный GitHub/GitLab-репозиторий.

**Почему нельзя бездумно делать rebase общей ветки?**

Потому что меняются хеши коммитов и история расходится с локальными копиями других разработчиков.

**Что такое Feature Flag?**

Механизм включения и выключения функциональности без обязательного изменения или удаления кода.

## 9. Минимальный рабочий сценарий DevOps

Начало новой задачи:

```bash
git switch main
git fetch origin
git pull --ff-only
git switch -c feature/my-task
```

Разработка:

```bash
git status
git diff
git add .
git diff --staged
git commit -m "Add my task"
```

Обновление feature-ветки:

```bash
git fetch origin
git rebase origin/main
```

Публикация:

```bash
git push -u origin feature/my-task
```

Затем создаётся Pull Request / Merge Request.

После проверки и одобрения изменения объединяются с основной веткой.

**Важно:** конкретный workflow зависит от правил компании и защиты веток. Не выполнять force push в общие ветки без согласования.
